# UniX — планировщик задач

UniX исполняет всю работу движка и игры как задачи. Задача описывается тремя заявленными параметрами и функцией. Планировщик измеряет фактическое CPU-время каждой задачи, сравнивает с заявкой и по результату корректирует классификацию, приоритет, нарезку параллельных циклов и частоту вызова.

## 1. Модель

### 1.1 Параметры задачи

```cpp
enum class Cost         : uint8_t { Low, Medium, High, Extreme };
enum class Priority     : uint8_t { Low, Normal, High };
enum class Significance : uint8_t { Sys, Engine, Actor, Task };
```

| Параметр | Смысл | Кто задаёт |
|---|---|---|
| `Cost` | заявленная ресурсозатратность | автор задачи |
| `Priority` | порядок внутри уровня значимости | автор задачи |
| `Significance` | класс задачи по роли | движок |

Значимость:

| Уровень | Назначение | Создаётся |
|---|---|---|
| `Sys` | критические процессы (связь, ввод) | только движком |
| `Engine` | внутренние процессы движка | только движком |
| `Actor` | исполнители подсистем: `Grave.Step`, `Amper.Prepare`, служебные задачи UniX | только движком |
| `Task` | задачи игры | пользователем |

Пользовательский API (`CreateTaskApi`) всегда создаёт `Significance::Task`. Внутренний `Scheduler::Create`, принимающий произвольную значимость, не входит в публичные заголовки.

### 1.2 Бюджет

Заявленному `Cost` соответствует доля целевого времени кадра `T = 1000 / targetFps` мс:

| Cost | Бюджет |
|---|---|
| Low | 2 % T |
| Medium | 8 % T |
| High | 25 % T |
| Extreme | 60 % T |

При `targetFps = 60`: 0,33 / 1,33 / 4,17 / 10 мс.

## 2. Использование

```cpp
TaskHandle h = UniX.CreateTask.NewTask("RayTraceTask", Cost::High, Priority::Normal, [](Task& t) {
    t.ParallelFor(8192, [&](uint32_t begin, uint32_t end) {
        for (uint32_t i = begin; i < end; ++i) { /* ... */ }
    });
});

UniX.CreateTask.Once("BuildLevel", Cost::Extreme, Priority::Low, [](Task& t) {
    while (!t.Cancelled()) { /* длинная работа */ break; }
});
```

Задача, созданная до начала кадра (например, в `OnStart`) или во время кадра, становится активной с ближайшего `BeginFrame`.

Все задачи `NewTask` выполняются в стадии Update, один раз за кадр, пока не будут остановлены (`Stop`, `Kill`).

## 3. Справочник API

### 3.1 `CreateTaskApi`

| Метод | Описание |
|---|---|
| `TaskHandle NewTask(std::string name, Cost, Priority, TaskFn fn)` | Задача, вызываемая каждый кадр. Бросает `std::invalid_argument` при пустой `fn`. |
| `TaskHandle Once(std::string name, Cost, Priority, TaskFn fn)` | Одноразовая задача. Если `Cost::Extreme`, уходит в фоновый поток и может выполняться несколько кадров; иначе выполняется один раз в стадии Update и удаляется. |

`TaskFn = std::function<void(Task&)>`.

### 3.2 `Task` — контекст выполнения

| Метод | Возвращает / делает |
|---|---|
| `float DeltaTime()` | время с предыдущего вызова **этой** задачи, с. При разгрузке (§4.4) включает пропущенные кадры |
| `double Time()` | время с запуска движка, с |
| `uint64_t Frame()` | номер кадра |
| `const std::string& Name()` | имя задачи |
| `Cost DeclaredCost()` | заявленная стоимость |
| `Cost EffectiveCost()` | стоимость, определённая UniX по факту |
| `Priority GetPriority()` | заявленный приоритет |
| `Significance GetSignificance()` | значимость |
| `float Utility()` | коэффициент полезности (§4.1) |
| `float LoadRatio()` | факт / бюджет заявки |
| `bool IsAsync()` | задача выполняется в фоновом потоке |
| `bool Cancelled()` | задача убита или движок завершается; длинным задачам следует выйти |
| `void Stop()` | завершить задачу после текущего вызова |
| `void ParallelFor(uint32_t count, Fn fn)` | параллельный цикл по `[0, count)`; `fn(begin, end)` (§4.5) |
| `T& State<T>()` | постоянное состояние задачи; живёт, пока жива задача; один тип на задачу |
| `void* Alloc(size_t bytes, size_t align = 16)` | скретч-память текущего вызова, сбрасывается перед каждым вызовом; только тривиальные типы |
| `T* AllocArray<T>(size_t n)` | то же, массив `n` элементов |

`State<T>()` создаёт `T` конструктором по умолчанию при первом обращении; деструктор вызывается при удалении задачи. Повторное обращение с другим типом в той же задаче недопустимо.

### 3.3 `TaskHandle`

| Метод | Описание |
|---|---|
| `bool Alive()` | задача существует и не убита |
| `void Pause()` / `void Resume()` | приостановить / возобновить вызовы |
| `void Kill()` | удалить задачу |
| `Stats GetStats()` | снимок статистики |

```cpp
struct Stats {
    float avgMs;        // EMA CPU-времени на вызов
    float utility;
    float loadRatio;
    Cost  effective;
    uint32_t throttle;  // 1 — каждый кадр; N — раз в N кадров
};
```

### 3.4 `UniXApi` (глобальный объект `UniX`)

| Метод | Описание |
|---|---|
| `CreateTaskApi CreateTask` | создание задач |
| `void SetTargetFps(float fps)` | целевая частота кадров; определяет `T` для бюджетов |
| `float TargetFrameMs()` | `T`, мс |
| `float FrameWorkMs()` | CPU-работа последнего кадра без ожиданий |
| `uint32_t WorkerCount()` | число воркеров |
| `LaneInfo Lanes()` | `{core, general, background}` — текущее распределение потоков по типам |
| `const char* GpuLanes()` | описание отображения GPU-очередей |

`EngineConfig::targetFps` задаёт начальное значение `targetFps`, `EngineConfig::workerThreads` — число воркеров (0 — авто).

## 4. Алгоритмы

### 4.1 Измерение и коэффициент полезности

В конце каждого кадра для задач, выполнявшихся в этом кадре, вызывается `UpdateStats`:

```
ms          = CPU-время вызова (сумма по потокам, без ожидания)
emaMs       = ms                          при первом измерении
            = 0.9 * emaMs + 0.1 * ms      далее
budget      = share(declared) * T
loadRatio   = emaMs / budget
```

Коэффициент полезности:

```
loadRatio >= 1      :  utility = 1 / loadRatio          (задача тяжелее заявки)
loadRatio <  1      :  utility = 1                      если declared == Low
                       utility = sqrt(loadRatio)        иначе (заявка завышена)
utility = max(utility, 0.01)
```

`utility = 1` — фактическая нагрузка совпадает с заявкой или меньше её у задачи `Low`; чем сильнее расхождение, тем ближе к 0.

Замечание: коэффициент измеряет точность заявки, а не пользу задачи для результата кадра. Это осознанное упрощение текущей версии.

### 4.2 Эффективная стоимость

По `emaMs` и `T` определяется фактический класс:

| Условие | Класс |
|---|---|
| `emaMs < 0.04 T` | Low |
| `emaMs < 0.15 T` | Medium |
| `emaMs < 0.40 T` | High |
| иначе | Extreme |

Пороги классификации и бюджеты заявок (§1.2) — разные величины: бюджет — допустимая доля, порог — граница класса.

Смена `effective` происходит только если новый класс удерживается 15 кадров подряд (гистерезис).

### 4.3 Эффективный приоритет

Только для `Significance::Task`:

| `loadRatio` | Действие |
|---|---|
| > 2 | приоритет −1 уровень |
| > 4 | приоритет −2 уровня |

Нижняя граница — `Priority::Low`. Заявленный приоритет не меняется, меняется `effectivePriority`.

### 4.4 Разгрузка (throttling)

Выполняется в конце кадра. `workEma` — EMA (0,9/0,1) CPU-работы кадра без ожиданий.

- Если `workEma > T` держится 10 кадров подряд, у каждой задачи с `Significance::Task`, `effectivePriority == Low`, не `Once`, из стадии Update `throttle` удваивается (максимум 8).
- Если `workEma < 0.7 T` держится 30 кадров подряд, `throttle` у всех задач Update уменьшается вдвое (минимум 1).

Задача с `throttle = N` вызывается раз в N кадров. Пропущенное время накапливается и добавляется к `DeltaTime()` следующего вызова. Логика, зависящая от шага (физика персонажа, интегрирование), должна использовать `DeltaTime()`, а не число вызовов.

### 4.5 `ParallelFor`

`lanes = workerCount + 1` (воркеры + вызывающий поток). Число кусков по `effective`:

| effective | Кусков |
|---|---|
| Low | 1 (выполняется целиком в вызывающем потоке) |
| Medium | `min(2, lanes)` |
| High | `lanes` |
| Extreme | `lanes * 4` |

Затем `chunks = min(chunks, max(1, count / grain))`, где `grain = 1` для High и выше и 16 для Low/Medium. Вызывающий поток выполняет нулевой кусок, остальные раскладывает по кругу в кольца main и воркеров (в начало кольца, на уровне значимости своей задачи), затем ждёт завершения и помогает выполнять чужие куски (`WaitAndHelp`).

Ограничение помощи: ожидающий поток берёт работу только из очередей с уровнем значимости не ниже уровня своей задачи (во избежание взаимных блокировок, например при ожидании `Grave.Step`, которому нужны куски пользовательского raycast).

Куски фоновых (`async`) задач ставятся в конец кольца фонового потока; остальные потоки забирают их в последнюю очередь, поэтому они не обгоняют кадровую работу. Сам фоновый поток работает с пониженным приоритетом ОС и, ожидая свои куски, помогает только с ними: возьми он кадровый джоб, барьер стадии ждал бы медленный поток (инверсия приоритетов).

### 4.6 Порядок внутри стадии

Задачи стадии сортируются: значимость по возрастанию (Sys первыми), `effectivePriority` по убыванию, `effective` по убыванию (самые тяжёлые первыми, эвристика LPT — сокращает общее время стадии). Затем джобы раскладываются по кругу в кольца main и воркеров, начиная с первого воркера: самые тяжёлые задачи оказываются у разных потоков.

### 4.7 Очереди и work stealing

У каждого потока (main, воркеры, фоновый) по одному кольцевому буферу джобов на каждый уровень значимости, у каждого кольца свой мьютекс. Поток ищет работу так:

1. обходит уровни в порядке своего типа (§4.9), пропуская уровни выше `maxBucket` и уровни, где по атомарному счётчику нет работы;
2. на каждом уровне берёт джоб из своего кольца, затем крадёт из колец других потоков, кольцо фонового потока — последним.

Пустые кольца проверяются без блокировки (атомарный размер). Счётчик уровня увеличивается до вставки джоба, поэтому он может быть больше фактического числа джобов, но не меньше: спящий воркер не пропустит работу. Воркеры будятся по числу новых джобов (`notify_one` на каждый, `notify_all` если джобов не меньше, чем воркеров); если никто не спит, мьютекс сна не трогается.

### 4.8 Склейка мелких задач

Задача считается мелкой, если её `effective == Low` и `emaMs < 0,05` мс (или она ещё не измерена и заявлена `Low`). Подряд идущие в отсортированном списке мелкие задачи одной значимости объединяются в один джоб, пока оценка суммы не достигнет 0,1 мс или 64 задач. Статистика по-прежнему считается для каждой задачи отдельно. На 2000 задачах по ~0,15 мкс работы это сократило время стадии примерно вдвое (§7).

### 4.9 Типы потоков

| Тип | Порядок обхода очередей | Назначение |
|---|---|---|
| Main | Sys-задачи, затем помогает остальным | отправка кадра |
| Core | Sys → Engine → Actor → Task | системная работа в приоритете |
| General | Task → Actor → Engine → Sys | пользовательская работа в приоритете |
| Background | отдельная очередь | `Once(..., Cost::Extreme, ...)` |

Раз в 60 кадров UniX пересчитывает число воркеров типа Core:

```
share   = ns(Sys + Engine + Actor) / ns(Sys + Engine + Actor + Task)
desired = clamp(round(share * workerCount), 1, workerCount - 1)
```

Текущее значение сдвигается к `desired` не более чем на один воркер за пересчёт. Пересчёт не выполняется при менее чем двух воркерах.

### 4.10 Перемещение задач между потоками

Задача может выполняться на любом воркере, но переносится только между вызовами: состояние хранится в записи задачи (`State<T>()`, статистика), а не в потоке. Приостановка задачи посередине вызова не поддерживается.

## 5. Потокобезопасность

- Методы `Task` вызываются из потока, выполняющего эту задачу.
- `TaskHandle` можно использовать из любого потока.
- Изменения мира из задач — через отложенные команды ([Architecture.md](Architecture.md#4-мир-и-отложенные-команды)).
- Доступ к собственному состоянию задачи из `ParallelFor`-кусков: куски выполняются параллельно, запись в общие данные требует атомарных операций или раздельных диапазонов.

## 6. Ограничения

- Кольца защищены мьютексами (по одному на кольцо), а не lock-free (Chase–Lev). Конкуренция за них низкая, но не нулевая.
- Зависимости заданы стадиями (Update → Simulate → Prepare) и барьерами, а не графом.
- Разгрузка затрагивает только пользовательские задачи стадии Update с низким эффективным приоритетом; код, чувствительный к пропуску кадров, следует писать через `DeltaTime()`.
- Производительность не сравнивалась с другими планировщиками.

## 7. Замеры

`UniXBench` (`cmake -DCE_BUILD_BENCH=ON`) меряет время стадий без окна и GPU:

```
UniXBench [workers] [tiny|pfor|mixed|all] [frames]
```

| Сценарий | Нагрузка |
|---|---|
| tiny | 2000 задач `Cost::Low` с ~0,15 мкс работы |
| pfor | 4 задачи `Cost::High` с `ParallelFor` на 200 000 элементов |
| mixed | 500 мелких + 2 `ParallelFor` в Update, Actor-задача с `ParallelFor` в Simulate |

Результаты на облачной машине с **2 ядрами** (среднее за 600 кадров, три прогона; разброс между прогонами до ±20 %):

| Сценарий | До (общие очереди) | После (кольца + склейка) |
|---|---|---|
| tiny, 6 воркеров | 1,28–1,32 мс | 0,57–0,60 мс |
| pfor, 6 воркеров | 0,55–0,63 мс | 0,47–0,60 мс |
| mixed, 6 воркеров | 0,79–0,98 мс | 0,72–0,92 мс |

На двух ядрах выигрыш от work stealing почти не виден: потоков больше, чем ядер. Значимы только цифры `tiny` (склейка). На 8-поточном CPU стоит повторить замер.
