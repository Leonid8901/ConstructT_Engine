# Архитектура

## 1. Соглашения

| Параметр | Значение |
|---|---|
| Система координат | правая, Y вверх, камера смотрит в −Z (`yaw = 0` → −Z) |
| Единицы | метры, секунды, радианы (углы в API; `SetFov` — в градусах) |
| `Mat3` | `m[row][col]` |
| `Mat4` | column-major, `m[col * 4 + row]` |
| Проекция | reverse-Z (ближняя плоскость → 1, бесконечность → 0), Y-flip под Vulkan |
| Кватернионы | `Quat{x, y, z, w}`, `Euler(pitch, yaw, roll)` применяет roll(Z) → pitch(X) → yaw(Y) |
| Примитивные меши | куб 1×1×1, сфера диаметром 1, плоскость `size × size` |
| Коллайдеры | не зависят от `Scale` сущности |

## 2. Кадр

```
Sys       главный поток   события окна, снимок ввода
Update    UniX            пользовательские задачи (параллельно)   → Flush мира
Simulate  UniX            Grave.Step (Actor)                      → события контактов и триггеров → таймеры → Flush → область мира → BVH лучей → агенты Nav
Prepare   UniX            Amper.Prepare (Actor)
Render    главный поток   TLAS → (каскады теней) → небо → инстансы → present
EndFrame  UniX            статистика, классификация, разгрузка, ребаланс потоков
```

Порядок вызовов в `Engine.cpp`: Update → Flush → Simulate → DispatchEvents → Timers.Update → Flush → EnforceBounds → RefreshQueries → Nav.Update → Prepare → Render → EndFrame.

Внутри стадии задачи выполняются параллельно; между стадиями — барьер. Задачи Simulate и Prepare внутренние (значимость Actor): `Grave.Step` и `Amper.Prepare`.

## 3. Модель потоков

- **Главный поток.** Sys-работа, запись и отправка кадра. В ожидании завершения стадии помогает выполнять задачи.
- **Воркеры.** Число по умолчанию `max(1, hardware_concurrency − 2)` (если ядер ≤ 2 — один воркер); задаётся `EngineConfig::workerThreads`. Каждый воркер имеет тип (lane): `Core` или `General`.
- **Фоновый поток.** Один, выполняет одноразовые задачи `Once(..., Cost::Extreme, ...)`, которые могут длиться несколько кадров.

Типы воркеров отличаются только порядком обхода очередей значимости (подробнее — [UniX.md](UniX.md#49-типы-потоков)).

## 4. Мир и отложенные команды

Хранилище сущностей постраничное: 4096 сущностей на страницу, страницы не перемещаются в памяти. Дескриптор `Entity` содержит индекс и поколение; после `Destroy` старые дескрипторы становятся невалидными (`Valid() == false`).

Модификации (`SetPosition`, `SetMesh`, `AddBody`, `Destroy`, …), вызванные во время стадии или из рабочего потока, не применяются немедленно. Каждый поток пишет их в собственный буфер команд; буферы применяются в точках синхронизации (Flush после Update и после Simulate). Вне стадий на главном потоке (например, в `OnStart`) команды применяются сразу.

`World.Spawn()` выделяет индекс и поколение сразу и возвращает дескриптор, поэтому цепочка `World.Spawn().SetMesh(...).AddBody(...)` корректна из задачи. Сама сущность создаётся при ближайшем Flush.

Следствия:

- Внутри стадии чтение (`Position()`, `Velocity()` и т. п.) возвращает состояние на начало стадии.
- В той же стадии `Valid()` для только что созданной из задачи сущности возвращает `false`, а чтение её полей даёт значения по умолчанию, пока не выполнен Flush.
- Два потока могут писать в мир одновременно без блокировок на стороне пользователя.
- Сначала применяются все созданные сущности (`Spawn`) из всех буферов, затем остальные команды: буферы в порядке номера потока, внутри буфера — в порядке записи. Поэтому сущность, созданная одной задачей и изменённая или удалённая другой в той же стадии, получит эти команды. Если две задачи одной стадии пишут в одно поле одной сущности, итог зависит от того, на каких потоках они выполнились, то есть не определён.
- Фоновые (`async`) задачи идут параллельно со стадиями: чтение мира из них может попасть на середину записи физики (например, позиция из прошлого и нового шага). Для логики, которой нужна согласованная картинка, используйте обычные задачи.
- Команда с устаревшим поколением (сущность уже уничтожена и слот переиспользован) отбрасывается.

## 5. Ввод

Снимок ввода делается один раз за кадр на стадии Sys. Нажатия и отпускания «защёлкиваются» и не теряются между кадрами. Читать ввод можно из любой задачи.

## 6. GPU-очереди

`GpuLanes` отображает логические лейны на очереди устройства:

| Лейн | Назначение сейчас |
|---|---|
| Graphics | запись и отправка кадра |
| Compute | сборка BLAS |
| Transfer | загрузка мешей |
| Present | презентация |

Если выделенной очереди нет, лейн откатывается на более общее семейство. Отправки защищены мьютексом. Буферы создаются с `VK_SHARING_MODE_CONCURRENT`, поэтому передача владения между семействами не требуется. Хелпер `Immediate()` выполняет разовую команду с ожиданием.

## 7. Vulkan

- Vulkan 1.3: dynamic rendering, synchronization2 (`vkCmdPipelineBarrier2`, `vkQueueSubmit2`).
- Память: VMA 3.3.0.
- Кадров в полёте: 2.
- Ray tracing: `VK_KHR_acceleration_structure` + `VK_KHR_ray_query`, определяется при создании устройства.
